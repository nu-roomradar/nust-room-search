# RoomRadar 運営ハンドブック

RoomRadar を引き継ぐ人・一緒に運営する人のための1枚。**「何が・どこで・いつ・壊れたらどうする」** だけを書く。
コードの読み方や手順の詳細は README と `.claude/skills/` にあり、守るべきルールは `CLAUDE.md` にある。
`[要記入]` はこの文書を書いた時点で分からなかった箇所。引き継ぎ時に埋めること。

最終更新: 2026-09-23

初めて参加する人は先に [`ONBOARDING.md`](ONBOARDING.md) を読む。

## 2.5 空き教室の使い方についての方針（2026-10-20 運営決定）

周知物（ポスター・紹介ページ・アプリ・Instagram）はすべてこの方針に合わせる。

**学生課の考え（2026-10-20 学生課長の指示より）**
- 静かな環境で学習したい人は、図書館または1号館の CST ギャラリーへ。
- 空き教室は自習専用のスペースではない。
- 空き教室はみんなで使う場所。静かさを求めすぎず、騒ぎすぎず、お互いの利用目的を尊重し、周囲に配慮して使う（**これが核**）。
- 使い方はいろいろ（個人学習・グループワーク・課題の相談・学生同士の打ち合わせ・授業の合間の休憩など）。

**核の言葉**
> 空き教室は、みんなで使う場所。使い方は人それぞれ。誰もが安心して使えるよう、お互いを尊重して、周りに配慮して使いましょう。

細かい注意（使い方の例／自習専用ではない・静かに学習したいときは図書館・CST ギャラリー／使う前にドア越しに軽く確認し、人がいたらひと声かける）は、この核の下に置く。

**RoomRadar の核の言葉（2026-10-21 運営決定）**: 「**「開けたら、空いてる」を当たり前に。**」。今後の周知物の中心に使う。「**探す5分、過ごす5分。**」は、まったく新しいデザインのポスターで使う（未着手）。静か版の代わりは「**空き教室、信じてる？**」と「**信じなくていい。確かめればいい。**」の2枚を隣同士で貼るポスター（未着手。新しいデザインなので学生課に改めて見てもらう）。「当たり前」は目指す姿の言い方なので、時間割にない授業がある旨の注意書きと必ず組で出す。お笑い系ポスター・Instagram 向けの格言もじり（「学生も歩けば授業に当たる。」「空き教室にも礼儀あり。」など）は候補として保留。

**言い方の軸**: 「空きコマに使える教室を、迷わず見つける」。「静か」「集中」「自習室」を売りにしない。図書館・学食など他の場所を下げる表現をしない。性別をネタにしない。

**決めたこと**
- 静か版ポスターは掲示しない。代わりに、教室探しの「あるある」をネタにした少しひねったポスターを1種類作る（学生課に改めて見てもらう）。
- アプリには図書館・CST ギャラリーの案内を入れる。紹介ページにも入れるが、今の注意書きくらいの控えめな扱い。
- 細かい決まり（飲食・電源・机の移動・消灯や空調・退出の目安・使えない教室）は学生課にメールで聞くが、曖昧なままでよい。問い合わせに答えるときは、決まっていないことを決まりとして言わず、各窓口の案内・理工学部学生課へ案内する。困ったとき（トラブル・知らない人に声をかけられた等）の相談先は学生課に確かめて書き足す。
- 正確さ: 大学の教室使用状況の情報を見せてもらい、アクセス権をもらったら取り込む。そのときに Instagram で告知する（「大学公式」と誤解されない言い方で、学生課に見てもらう）。取得データは公開リポジトリに入れない。
- 結果報告用に、使った目的をワンタップで聞く仕組みを作る（選択肢は学生課の例に合わせる。匿名・全体の集計のみ。性別などは聞かない。教室ごと・時間ごとの細かい形では出さない）。テスト終盤の利用者アンケートに「空き教室を安心して使えましたか」を任意で入れる。
- ポスター・動画・Instagram は、出す前に運営メンバーの女子学生にも見てもらう。

**「利用人数の目安」（裏で準備中。公開は学生課の了承後）**
- 機能と画面は裏で作って詰めてよい。テスト運用中に「新機能」として出したいので、学生課に相談して了承を得てから公開する（企画書・CLAUDE.md では「テスト運用後」としていたので、その変更として伝える）。
- **学生課に提案するときに必ず押す要素: 安心感。** 正確な人数を教室ごとに出すと「この教室には1人しかいない」と分かり、一人で使っている人を探すのに悪用されうる。そこで、人数は「空いている／少なめ／多め」のような大まかな段階で示し、少ない人数は表示しない・少し遅らせて表示するなどを最初から組み込む。誰もが安心して使えることを目的に据える（学生課の「お互いの尊重・周囲への配慮」と同じ方向）。
- 場所を取る・押さえる働きは持たせない（仮予約の言い換えに見えないように）。名前などの個人情報は扱わない。

## 4.5 Instagram トークンの自動更新

`IG_ACCESS_TOKEN` は発行から **60日で失効**する。2026-08-13 に切れたときは気づくまで3週間かかり、その間まったく投稿できなかった。手で再発行し続けるのをやめるため、`.github/workflows/ig-token-refresh.yml` が**毎月1日に60日先まで延長**して Secret を書き換える。

**仕組み**: `refresh_access_token` で新トークンを取得 → 実際に使えるか確認 → 確認できてから Secret を更新。検証に失敗したら Secret は触らない（古いトークンが残るので投稿は続けられる）。

**必要な準備（一度だけ）**: GitHub Actions は `GITHUB_TOKEN` では Secret を書き換えられないので、専用の PAT が要る。

1. GitHub の自分のアイコン → **Settings** → 一番下の **Developer settings**
2. **Personal access tokens** → **Fine-grained tokens** → **Generate new token**
3. 設定:
   - **Resource owner**: `nu-roomradar`（個人アカウントではなく Organization。※ 組織の承認が要る場合がある）
   - **Repository access**: Only select repositories → `nust-room-search`
   - **Repository permissions** → **Secrets** を **Read and write** に
   - **Expiration**: **1年**（無期限にしない。漏れたときに永久に使われないように。2026-10-22 点検）。年1回の作り直しは「3. 定期作業カレンダー」に合わせる
4. 生成されたトークンをコピー
5. https://github.com/nu-roomradar/nust-room-search/settings/secrets/actions → **New repository secret**
   - Name: `IG_REFRESH_PAT`
   - Secret: コピーしたトークン
6. Actions タブ → 「Instagramトークンの自動更新」→ **Run workflow**（`dry_run` を **true**）で疎通確認

**失敗したときは**: Actions が赤くなり、週次の運用ヘルスチェックが Issue で知らせる。ログを見て切り分ける。

| ログ | 意味 | 対応 |
|---|---|---|
| `既に失効しています` (code=190) | 延長できる期限を過ぎた | **自動では直せない。** Meta for Developers で手動再発行（`.claude/skills/instagram-post/SKILL.md`） |
| `Secret の公開鍵を取れません` | PAT の権限不足・期限切れ | PAT を作り直して `IG_REFRESH_PAT` を差し替える |
| `新しいトークンが使えません` | Meta 側でアプリ設定が変わった等 | Secret は無事。Meta のアプリ設定を確認 |

トークンはログに出ない（長さと末尾4文字だけ）。

## 4.6 GA4 週次の記録（2026-10〜）

`.github/workflows/ga4-weekly.yml` が毎週月曜 6:07 JST に `scripts/fetch_ga4_metrics.py` を回し、直前の1週（月〜日）の利用状況を `data/ga4_weekly.md`（表）と `data/ga4_weekly.json` に追記する。アプリと LP はドメインが別なので分けて記録する。ダッシュボード用の `data/ga4_history.json`・`ga4_breakdown.json`（直近28日）も更新する。
2026-08 までの取得が毎回失敗していたのは、下の Secrets が未設定だったため。

**最初の設定（運営者の作業・1回だけ。iPad は Safari の「デスクトップ用Webサイトを表示」で）**
1. https://console.cloud.google.com/ でプロジェクトを作る（名前は roomradar など）。
2. 「API とサービス」→「ライブラリ」で **Google Analytics Data API** を有効にする。
3. 「IAM と管理」→「サービスアカウント」→ 作成（名前は ga4-reader など。ロールは付けなくてよい）。
4. 作ったサービスアカウント →「鍵」→「鍵を追加」→「新しい鍵を作成」→ **JSON**。ファイルがダウンロードされる（再取得できないので保管）。
5. GA4（https://analytics.google.com ）→ 管理 → **プロパティのアクセス管理** → ＋ → 手順3のメールアドレス（`…@….iam.gserviceaccount.com`）を **閲覧者** で追加。
6. GA4 → 管理 → **プロパティの詳細** の「プロパティ ID」（数字）を控える。
7. https://github.com/nu-roomradar/nust-room-search/settings/secrets/actions で2つ登録する。
   - `GA4_PROPERTY_ID` … 手順6の数字
   - `GA4_SA_KEY` … 手順4の JSON ファイルの中身を丸ごと
8. Actions →「GA4 週次の記録」→ Run workflow（weeks に `4` を入れると直前4週を取り直す）。`data/ga4_weekly.md` に表が出れば完了。

**検索条件の内訳**（校舎・曜日・時限）を取るには、GA4 → 管理 → カスタム定義 → カスタムディメンションに `search_building`・`search_day`・`search_period`（範囲＝イベント）を登録する。未登録でも週次の記録は取れる（警告が出るだけ）。

**失敗したとき**: `Secrets … が設定されていません` → 手順7。`PERMISSION_DENIED` → 手順5（閲覧者の追加漏れ・別プロパティ）。`API has not been used` → 手順2。

## 4.7 「実は使われていた」報告の保存場所と見方

**中身は残らない。残るのは GA4 の件数だけ。**

| どこに | 何が | いつまで |
|---|---|---|
| Render のサーバー上の `reports.db`（SQLite。`app.py` の `REPORTS_DB`） | 教室・曜日・時限・取り消しコード・期限・報告者（IP を塩付きハッシュにした16文字。IP そのものは保存しない） | **その時限が終わると消える**（検索・報告のたびに期限切れを削除）。再デプロイ・再起動でも全部消える |
| GA4 のイベント `report_room` | 報告が成立した回数（パラメータに `building`・`room` が付く） | GA4 の保持期間のあいだ |

**見方**
1. **いまの報告**：検索アプリでその曜日・時限を検索する。報告がある教室のカードに「⚠N件報告」、2人以上で「使用中の可能性」（グレー）と出る。一覧で全件を出す画面・API は無い（作っていない）。
2. **週ごとの件数**：`data/ga4_weekly.md` の「「使われていた」報告」列（毎週月曜に自動記録）。運営用ダッシュボードの「イベント発生数 → 使用中報告」は直近28日の件数。
3. **どの教室が報告されたか**：`data/ga4_weekly.md` の下の「報告の多い教室（直近28日）」（毎週月曜に自動記録。上位10室）。GA4 のカスタムディメンション `room`（予約/報告-教室）・`building`（予約/報告-校舎）は 2026-06-18 に登録済みなので、6月からのデータがある。この2つは廃止した仮予約（`reserve_room`）と共用なので、GA4 の「探索」で見るときはイベント名 `report_room` に絞る。偽の記録を避けるため、自動記録は教室マスタにある教室名だけを数える。
4. **サーバー上の DB を直接見る**：Render のダッシュボードの Shell が使えるプランなら、`sqlite3 reports.db "SELECT room, day, period, expires_at FROM reports"` で見られる。ただし期限切れの分はもう無い。

報告の上限：1人（接続元）が1つの曜日・時限に報告できるのは3教室まで（`REPORT_MAX_ROOMS_PER_PERIOD`）。教室マスタに無い教室名は受け付けない。

## 4.8 セキュリティの点検と、事故のとき（2026-10-22）

**きっかけ**: 2026-10-21 夜、首相が PHP の重大な脆弱性（CVE-2026-109618／109619、通称 php2shell）の修正を急ぐよう呼びかけた。背景は 10 月に相次いだ不正アクセス・個人情報漏えい（政府はプログラムの更新と多要素認証の徹底を求めている）。
**RoomRadar は PHP を使っていないので直接の影響は無い**（本番は Render の Python/Flask、LP とダッシュボードは GitHub Pages の静的ページ）。あわせて全体を点検し、次を直した。

| 直したこと | 理由 |
|---|---|
| Actions の pip を、版とハッシュで固定したファイル（`.github/requirements/`）から入れる | 版なしだと、PyPI のパッケージが乗っ取られたとき次の定期実行で入り、Secrets を盗まれる（10 月の GhostAction など GitHub 経由の攻撃が実際に起きている） |
| Action をコミット SHA で固定。push しないジョブは checkout のトークンを残さない | タグの付け替えによる乗っ取り対策 |
| トークン延長で通信エラーが起きたとき、新しいトークンがログに出ないようにした | 公開リポジトリの Actions ログは誰でも読める |
| アプリが受け取る本文を 16KB までにした。おかしな形の JSON は 400 にする | 巨大な本文でメモリを使い切らせて落とせた（落ちると報告も消える） |
| 本番の間接依存（Werkzeug・Jinja2 など）も版を固定 | デプロイのたびに何が入るか分からなかった |
| `.gitignore` に `.env`・鍵ファイルを追加 | 公開リポジトリに誤って上げないように |

`tests/test_workflows.py` が、Action の SHA 固定・pip のハッシュ固定・トークンを残さない設定が崩れていないかを毎回検査する。依存の版を上げるときは `.github/requirements/README.md` の手順で作り直す。

**運営者がアカウント側でやること（コードでは直せない）**
- [ ] GitHub（運営者の2アカウント）で2段階認証を有効にする（認証アプリかパスキー。SMS は避ける）。リカバリーコードを GitHub とメールの外に保管する

## 4.9 教務課の教室使用予定の取り込み（仮。2026-10-22〜）

**経緯**: 2026-10-22、理工学部学生課から「教務課の教室予約データが提供されたら、リアルタイムで反映できるか」と聞かれた。教務課のシステムから**自動で読み取る形**になる見込みで、**予約（授業以外の使用予定）が入っている時間帯の教室は、画面では「空き」に出さない**ことで運営が了承した。データの形式と受け取り方は後で学生課から知らされるので、**仮の仕組みを先に作っておき、形式が来たら最終調整して出す**。

**仕組み**（`school_bookings.py`）
- 環境変数 `SCHOOL_BOOKINGS_URL`（https の読み取り先）か `SCHOOL_BOOKINGS_FILE`（ファイル）が**無ければ何もしない**。いまの本番はこの状態で、動きは変わらない。
- 読み取りに鍵が要るなら `SCHOOL_BOOKINGS_TOKEN`（`Authorization: Bearer` で送る。形が決まったら合わせる）。何秒おきに読み直すかは `SCHOOL_BOOKINGS_INTERVAL`（既定 300 秒）。
- 読み取りは検索の応答とは別のスレッドで行う（gunicorn のワーカーごとに1本。`SCHOOL_BOOKINGS_INTERVAL` 秒おき、60秒〜3時間に収める。書き間違えても既定の300秒になり、アプリは落ちない）。上流が遅くても検索は待たされない（全体の締め切り15秒）。ワーカーの起動から1秒のあいだだけ、最初の読み取りを待つ。
- 読めない応答（ログイン画面の HTML・空・見出しに日付と教室が無い・JSON がオブジェクトの配列でない・1行も使えない）は**失敗**として扱い、前回の内容を使い続ける。失敗したら60秒後に読み直し、続けば間隔を倍にしていく（最大30分。通常の間隔のほうが長ければそちら）。最後にうまく読めてから6時間を過ぎたら使わない（＝時間割だけの表示に戻る）。見出しだけの CSV や `[]` は「予定なし」として正しく読む。
- 転送（リダイレクト）は追わない。鍵は転送先に送らない。読み取り先は https に限る。
- 時間割の教室と照合できなかった教室の数（名前は出さない）と、読めなかった行の数を、ログと `school_bookings.status()` に出す。
- いまの年度・学期を見ているときだけ、その曜日・時限が次に来る日の予定を見て、予定のある教室を「空き」から外す（「何限まで空いているか」も予定の手前までにする）。
- **個人情報**: 使うのは日付・時間帯・教室だけ。予約者名などほかの列は読み込んだその場で捨てる。データはサーバーのメモリにしか置かない（ディスクにもリポジトリにも書かない）。再起動したら読み直す。
- 画面では「予約」と書かない（CLAUDE.md ルール3）。

**仮の形式**（CSV。1行目は見出し。列の順番は問わない。UTF-8 か Shift_JIS）
```
日付,開始,終了,教室,（そのほかの列は無視）
2026-10-23,10:50,12:30,S303,…
```
時刻の代わりに「時限」列（`2`、`２限`、`2-3`）でもよい。同じ見出しの JSON 配列でもよい。時刻が授業時間に少しでもかかれば、その時限は使えないとみなす。時刻も時限も無い行と、「終日」「全日」「－」と書いた行は、その日は終日使えないとみなす（空きに出さない側）。終了「0:00」は夜中の0時まで。合同の略記（`1456/7/8`・`521/2/…/10`）は時間割 DB と同じ規則（規則D）で分け、`S303/S304`・`1111・521` のような教室コードの並びも分ける。教室名と施設名の列が両方あれば教室名を使う。空行・授業時間にかからない予定（休み時間・夜間・7限など）は無視する。期間（`10/26～10/30`）は今は読めない行として数える。

**形式が来たらやること（最終調整）**
1. サンプルを `tests/test_school_bookings.py` に（個人名などは架空のものに置き換えて）足し、`school_bookings.py` の `COLUMNS`（見出しの言い方）と `parse_text`（形式）、`_read_source`（受け取り方：ログインが要る画面なのか、ファイルの置き場所なのか）を合わせる。
2. 照合できなかった教室の数（`status()["unmatched"]`・ログ）を見て、教室名の書き方が時間割と違えば、照合（`room_keys`）に別名の表を足す（例: 「1511」→「1511電気実験室」。実データを見てから決める）。
3. 画面に「教務課の使用予定も反映しています」などの一言を出すかを決める（出すなら画面の変更なのでルール5の確認）。
4. Render の Environment に読み取り先と鍵を入れる（**リポジトリには書かない**）。本番で数件、予定のある教室が空きに出ないことを確かめてから、学生課に知らせる。
- 教室の1週間の画面（`room.html`）に今週の予定を出すのは未対応（必要なら最終調整のときに足す）。
